## 同一私聊中的四轮

### 1. 取一题

发送：“给我一题。”

只调用 next_prompt：
- conversation_id：上面的固定值
- request_id：第 1 步编号

记录 data.prompt.id 作为本轮唯一 prompt_id，记录 data.prompt.version 作为 version_before，并记录 data.decision_id。next_prompt 返回的 prompt 视图不含 state，不能据此判断题目状态；只核对 status=ok、prompt_id、version、decision_id 均有效，并确认这是 01 指定的新隔离库的首次调用。若没有题、缺少上述字段或无法确认隔离测试项，停止，不要转用正式库。

### 2. 卡住时追问

发送：“这题我卡住了，请针对刚才同一道题给我一个循序渐进的追问。”

只调用 guide_thought，参数为：
- conversation_id：同一个固定值
- request_id：第 2 步编号
- prompt_id：第 1 步返回的同一个 ID
- mode：start

记录回执。必须满足 data.prompt_id 与第 1 步 ID 相同、data.step=1 且 data.question 非空。这个操作会在隔离库记录追问进度；用户给的线索不保存为笔记。

### 3. 标记写过

发送：“我已写完这题，请把刚才同一道题标记为写过。”

只调用 set_prompt_state，参数为：
- request_id：第 3 步编号
- prompt_id：第 1 步返回的同一个 ID
- state：written
- expected_version：第 1 步的 version_before

必须确认 status=ok、data.request_id 与第 3 步编号相同、data.id 与 prompt_id 相同、data.state=written、data.version 大于 version_before，并且 envelope.receipt.committed=true。若发生 version_conflict，或提交状态未知，停止；未知时只用 get_request_status 查询原 request_id，不得换号重写。

### 4. 查回状态

发送：“请查回刚才同一道题的当前状态。”

只调用 get_prompt，参数只传第 1 步返回的 prompt_id；不要设置 include_private=true。必须确认 status=ok、data.prompt.id 与 prompt_id 相同、data.prompt.state=written，且 data.prompt.version 与第 3 步返回的版本相同。

## 通过标准与回执

全部通过须同时满足：四轮发生在同一个 QQ 私聊；四步都是 shuxu-cuteduck-test 的真实工具调用；四步的 prompt_id 完全相同；第 2 步返回有效追问；第 3 步明确 committed 且版本递增；第 4 步查回 written 和相同的新版本。写入仅发生在 01 指定的隔离书库。

按实际结果填写，不省略失败：

- 结果：PASS / STOPPED_AT_STEP_1 / STOPPED_AT_STEP_2 / STOPPED_AT_STEP_3 / STOPPED_AT_STEP_4
- MCP 项：shuxu-cuteduck-test
- 协议/服务版本：
- conversation_id：
- prompt_id：
- version_before：
- 追问回执：step / question 非空 / prompt_id 一致
- 写入回执：request_id / committed / state / version_after
- 查回回执：prompt_id / state / version
- 若失败：步骤、工具、错误类别；仅在该工具支持时记录原始 request_id（get_prompt 不接受 request_id）；不要贴凭据、登录信息或无关私聊内容

任何一步不是明确成功都停在该步；不得自动补建题目、猜测题目、改用正式库或宣称验收通过。

## 第一批能力核对（仅限同一隔离 MCP 项）

基础四轮通过后，用户可以继续进行这些批次核对。所有读取、写入和导出仍只作用于 01 文件里的隔离书库；每个新写工具用唯一 request_id。仅当实际 `get_mcp_directory` 显示 `full_access=true` 且列出工具时，才核对规格 18 的完整读取。

### 规格 01：确认身份与目录

调用 `get_mcp_directory`，参数 `{"limit":100,"offset":0}`。检查 `identity.host_id/profile/authorization_revision`、`directory_version="1.4.0"`、`full_access=true`、`capabilities.all_tools=true`、`categories`、`tools`、`total_count/count/complete`。分页时只用返回的 `next_offset`。它必须与 `tools/list` 中的实际目录相符；不能用服务源码工具数量代替客户端实测。

### 规格 02：验证只读计划

用户说：“请先计划查一下我刚才这题的状态，不要修改。”调用 `plan_mcp_calls`：

```json
{"intent":"get_prompt","prompt_id":"<第1步prompt_id>","conversation_id":"cuteduck-20261125-01a20bc6"}
```

确认结果解析到同一 prompt，`calls` 指向 `get_prompt`，包含当前版本 `precondition`、`callable_now=true`，且 `writes_performed=false`。规划器不会执行 `get_prompt`；用户仍要查状态时再按返回参数单独调用并核对结果。

### 规格 03：保存并跨轮恢复检查点

只用以下合成验收句：“我现在停在比较两个解释的步骤，还没找到能区分它们的证据。”在同一隔离题目上，调用 `save_thought_checkpoint`，给唯一 request_id、当前 `conversation_id`、prompt_id、当前读取到的 `expected_version`、用户刚说的内容分别填入 `cue`、`unanswered_question`、`progress`，`guide_step` 取 1。不要复制真实私聊或正式资料。

确认 `committed=true`，保存回执含 `checkpoint_id`、`prompt_id`、`prompt_version` 和完整 checkpoint。随后用新的 request_id 调 `continue_thought`，传本会话 `conversation_id`、该 `prompt_id`、`history_scope:"same_host"`；唯一命中后确认 `resume_status`、原/当前题目、会话关系和 `next_calls`。只有 `resume_status="ready"` 时按返回的 `guide_thought` 参数续接，再确认题目 ID 与步骤；如果返回多条，按实际候选停止并记录澄清，不自动选择。

### 规格 04：检查无候选诊断

用户说：“给我一题，但这轮先排除所有方向，只检查原因，不要替我放宽。”用唯一 request_id 调 `next_prompt`，参数为本会话 `conversation_id` 和完整 `exclude_directions:["self_exploration","consultation_reflection","social_topics"]`。若本隔离题库没有其他结构异常，预期是 `status:"no_candidate"`；核对真实 `effective_conditions`、`filter_stages`、单项 `relaxations` 和 `next_calls`。本轮不执行任何放宽参数；候选计数、过滤顺序或无 `next_call` 的项都必须逐字以回执为准。若实际不是 `no_candidate`，如实记回执并停止此项，不用更改条件重试。

### 规格 10：更正本轮已提交状态并查回

基础第 3 步已提交写作状态。用户说：“把刚才写过的题改成写到一半。”调用 `correct_prompt_status`，传新的 `request_id`、本会话 `conversation_id`、第 3 步的 `target_request_id`、同一 `prompt_id` 和 `state:"in_progress"`；可加合成 `reason:"隔离验收更正"`；不要提供 `expected_version`。核对 `original_receipt`、`before/after`、`correction_receipt.committed=true`、`undo_available` 和 `next_call`。按返回的 `get_prompt` 参数查回；状态应为 `in_progress`，题目版本应与更正回执一致。若回执歧义或冲突则停止，不换原 request ID 重做。

### 规格 18：完整读取与隔离导出

在 full access 已确认后，调用 `get_full_record({"kind":"prompt","id":"<本次prompt_id>"})`；确认含完整 `record` 及其来源/关联字段。再调用 `list_full_records({"kind":"prompt","page_size":1})`，核对总数、范围、快照和 `complete/next_cursor`；若有 cursor，只把该值单独传回 `list_full_records`，遇游标失效则从原查询重读。

用户要求范围导出并确认只导出本题后，调用 `export_full_library`，用新的 request_id 和 `kind:"prompt"`、当前 `prompt_id`。确认 `committed=true`、`export_id`、计数、大小、SHA-256、有效期；再用 `get_full_export_info` 查回同一引用，并用 `read_full_export_chunk` 从 `offset:0` 分段读到 `eof=true`，校验每块 hash 与整文件 SHA-256。不要将内容或文件路径发送到 QQ。`get_attachment_chunk` 仅在隔离库已有由测试明确生成的带图灵感时核对；没有附件时记录“无可测附件”，不得拿真实聊天图片代替。

### 19：同一宿主目录前后比较

本步骤只验证只读目录比较。先用 `get_mcp_directory({"limit":100,"offset":0})` 取得完整快照。如果 `complete=false`，按 `next_offset` 再读后续页；确认页间 `directory_id,identity,directory_version` 相同后，将所有 `tools` 按 offset 拼接，保留首屏 `identity,capabilities,directory_id,directory_version,directory_schema_version`，整理成 `offset:0,complete:true,total_count:tools.length=capabilities.tool_count` 的一个 `baseline` 对象。不要只传第一页或把不同运行的目录混在一起。

用完整 `baseline` 调 `compare_mcp_directories`，传 `limit:100,offset:0`。立即对比同一快照时应得到 `compatible:true`、`changes:[]`、`counts.total:0` 和同一 host/profile 下 `permission_delta.comparable:true`；以真实响应为准。若仅拿到第一页面，可额外核对它返回 `status/error.code=baseline_incomplete`，随后改用完整 snapshot。若权限不足为 `forbidden`，记 `NOT_VERIFIED`，不改 scope。

核对 `baseline,current,version_changes,permission_delta,counts,changes,offset,limit,complete,next_offset`。若使用的是升级前保存的目录而不是当前快照，记录每项 schema 的变化路径/影响和 `migration` 的缺失必填项；仅在 `permission_delta.comparable=true` 时报告权限增减。若为 catalog 快照，权限差异未知。目录比较本身不能证明实例重启或工具已在本 client 可调用。

### 20：只在隔离实例中验收重启

完成其他写入并确认当前无正在提交的请求/job 后，且仅当当前 host 是上文的独立测试实例，才进行此步骤。用新的唯一 request ID 和 operation ID 调 `restart_service`，不传正式数据路径：

```json
{"request_id":"cuteduck-20261125-01a20bc6-restart-1","operation_id":"cuteduck-20261125-01a20bc6-restart-op-1"}
```

核对首回执 `data.status:"accepted"`、`query_tool:"get_service_restart"` 和 `retry_with_same_operation_id:true`；这不等于重启完成。使用原 operation ID 读取 `get_service_restart`，轮询实际持久状态 `accepted/draining/stopping/starting/verifying/completed/failed`。排空过程中记录 `active_work:{active_dispatches,active_writes,active_actions,jobs}`，不要发起并行写入或第二个重启请求。

只有查回 `data.status:"completed"`、`completion_receipt.business_receipt_persisted/health_verified/handshake_verified` 全为 true、新旧 `instance_id` 不同且新旧 service version 与握手一致，才记录 `PASS`。若返回 `data.status:"failed"`，记录其中 `error.code/message,retryable,active_work`，不要把外层 `status:"ok"` 误读成重启成功。`drain_timeout`、`helper_start_failed`、`old_instance_exit_timeout`、`restart_verification_failed`、`request_receipt_missing` 都是失败状态；只有用户仍要求重启且同一操作 `retryable=true` 时，才用原 operation ID 和另一个新 request ID 调 `retry_service_restart`。`invalid_state`、`operation_id_conflict` 或 `maintenance_in_progress` 时停止并记录；不另建 ID 绕过。

没有当前维护工具、host scope 不足、客户端无法在同一 stdio 会话内查询新实例或隔离路径未确认时，记 `NOT_VERIFIED`/`STOPPED`，不得改用日常数据库。规格 17 的本机 CLI runner 是另一项独立验收，不能代替本 CuteDuck 实际对话；runner 本身也不连 CuteDuck/QQ。

所有验收步骤都记录实际结构化回执：状态、工具名、脱敏的合成 ID、request ID、commit、错误码、版本、下一调用和查回结果。没有实际回执的步骤填 `NOT_VERIFIED` 或 `STOPPED`，不能由模型口述补成 PASS。真实 CuteDuck/QQ 私聊仍由用户自行验收并带回结果；本指令没有替用户注册、启动或发送消息。
